asn1click decodes, encodes, converts and generates ETSI C-ITS messages (CAM, DENM, CPM, VAM, MAPEM, SPATEM, IVIM, SREM, SSEM) in their binary (UPER, WER) and readable (JSON, XML) encodings. Use it from the browser, from an AI assistant, or from your own code.

Quick start

Decode a payload

  1. Open the Web tools and paste a UPER payload as hex (a leading uper: is fine).
  2. Pick the output format, for example JER (JSON), and press Convert.
  3. The result opens in a tab. Its label says which definition was used, e.g. auto-detected as _cam_v2_3.

The same from a terminal:

curl -X POST "https://api.asn1click.com/convert" \
  -H "X-From: UPER" -H "X-To: JER" \
  --data "uper:02020000000000000006b49d200d693a40000000000030d4000000000000000000028003ff01fff800"

From an AI assistant

Add https://mcp.asn1click.com/mcp as a remote MCP server and ask, for example, "Generate a CAM of a car at 50 km/h and encode it in UPER". See AI assistants.

Key ideas

  • Encodings. UPER and WER are binary (exchanged as hex); JER (JSON, X.697) and XER (XML, X.693) are readable. All four follow the standards and check every constraint: a value outside its range is an error in any format.
  • Which definition. UPER is not self-describing. For ETSI messages the version is read from the ITS PDU header (protocolVersion + messageID): this is auto-detect. You can also name a definition: a message such as _cam_v2_3, or a raw type such as _cam_v2_3:CAM.
  • Encoding rules. The default is X.691 as written (like Objective Systems and asn1tools). The asn1c / Vanetza rules reproduce asn1c-based stacks, which differ in a few constraints.
  • Field names are exactly those of the ASN.1 (long, node-XY1).
